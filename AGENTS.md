# AGENTS.md

Этот файл задаёт обязательный контекст для AI-агентов и разработчиков, работающих с AI Video Factory.

## Текущее состояние

- Проект находится на стадии bootstrap.
- `Ai_Video_Creator.slnx` содержит каркас Host и первого бизнес-модуля, но прикладной конвейер ещё не реализован.
- Наличие компонента в `README.md` означает план, а не готовую реализацию.
- Не заявляйте, что функция работает, пока она не реализована и не проверена сквозным тестом.

## Цель первой версии

Построить персонального Telegram-агента для одного пользователя:

```text
video + user comment -> analysis -> edit plan -> Remotion -> verified MP4 -> Telegram delivery
```

Базовый результат одного задания: один проверенный вертикальный MP4 из одного исходника.

## Границы MVP

Сначала реализуйте:

- Telegram allowlist для одного user ID;
- локальное хранение;
- SQLite job store;
- последовательную обработку;
- FFmpeg/FFprobe;
- условную транскрипцию Whisper;
- ограниченный JSON-контракт монтажного плана;
- как минимум один фиксированный Remotion-шаблон;
- проверку MP4;
- доставку MP4 через Telegram.

Не добавляйте без отдельной задачи:

- микросервисы;
- Redis, PostgreSQL или брокер сообщений;
- Kubernetes;
- распределённый рендер;
- multi-tenant модель;
- web-панель;
- автоматическую публикацию в соцсети;
- обучение по статистике просмотров;
- свободную генерацию React-кода через LLM.

## Архитектурные границы

### Модульный монолит и Clean Architecture

- Система строится как модульный монолит. Первый бизнес-модуль называется `VideoProduction`.
- Каждый бизнес-модуль разделяется на проекты `Domain`, `Application` и `Infrastructure`.
- Зависимости направлены только внутрь: `Infrastructure -> Application -> Domain`.
- `Domain` не зависит от Host, Infrastructure, внешних SDK и других модулей.
- `Application` зависит только от `Domain` своего модуля и явно введённых межмодульных контрактов.
- `VideoFactory.Bot` является Host, Telegram-адаптером и composition root. Бизнес-правила в нём запрещены.
- Модуль не обращается к Infrastructure другого модуля. Межмодульное взаимодействие проходит через явные контракты.
- Не создавайте общие проекты `Core`, `Infrastructure` или `SharedKernel`. Общий код выделяется только после появления второго реального потребителя.
- Node и Python являются внешними адаптерами, а не бизнес-модулями.
- Unit-тесты проверяют `Domain` и `Application`; integration-тесты проверяют `Infrastructure` через application seam.

### C#/.NET

C# является единственным оркестратором и владельцем бизнес-состояния. Здесь находятся:

- state machine задания;
- очередь и восстановление;
- лимиты и политика повторов;
- монтажные контракты;
- генерация одного монтажного плана;
- адаптеры внешних сервисов;
- запуск FFmpeg, Python и Node;
- финализация проверенного артефакта и Telegram delivery.

Не дублируйте бизнес-оркестрацию в Node или Python.

### SQLite

SQLite является источником истины для заданий. In-memory `Channel` допустим только как сигнал о новой работе.

Каждый этап должен быть идемпотентным. После перезапуска приложение должно определить, что уже завершено, и продолжить с безопасной точки.

Не храните медиафайлы как BLOB. В БД хранятся пути, hashes, metadata и состояния.

### Node и Remotion

Node должен быть узким `render-host` с командами наподобие:

```text
render-host validate --job <request.json>
render-host list-templates
render-host render --job <request.json>
```

Требования к процессу:

- вход передаётся JSON-файлом;
- `stdout` содержит структурированные события;
- `stderr` содержит диагностику;
- exit code отражает результат;
- поддерживаются timeout и отмена;
- результат сначала пишется во временный файл;
- готовый файл публикуется атомарным переименованием.

Remotion визуализирует монтажный план. Не помещайте в React-компоненты выбор сцен, вызовы LLM, управление очередью или доступ к SQLite.

### Python

Python допустим для Whisper и компьютерного зрения. Он не является вторым приложением и не владеет состоянием задания. Обмен с .NET выполняется через versioned JSON и файлы.

### FFmpeg

Запускайте FFmpeg и FFprobe через API процессов без shell interpolation. Пользовательские строки никогда не вставляются в командную оболочку.

Оригинал сохраняется неизменным. Для анализа и рендера создаётся нормализованный mezzanine при необходимости.

## Монтажный контракт

Монтажный план должен быть:

- версионируемым;
- детерминированным;
- валидируемым JSON Schema;
- независимым от конкретного LLM-провайдера;
- достаточно общим для нескольких Remotion-шаблонов;
- привязанным к существующим source asset IDs, а не произвольным путям.

Храните отдельно:

- время оригинального источника;
- время нормализованного или очищенного master;
- output timeline текущего Variant.

Для каждого используемого сегмента должна существовать явная связь выходного интервала с исходным интервалом.

LLM может выбирать только из известных фрагментов и допустимых операций. Не разрешайте ей придумывать файлы, таймкоды, шаблоны или неподтверждённые факты.

## Несколько вариантов после MVP

Первый MVP создаёт ровно один Variant и не включает ZIP. Не добавляйте конфигурируемое количество вариантов, сравнение их различий или упаковку в ZIP без отдельной задачи после завершения сквозного сценария одного MP4.

При последующем расширении не создавайте копии, различающиеся только темой. Разнообразие оценивается по нескольким признакам:

- hook и первый кадр;
- выбранные source segments;
- порядок сегментов;
- длительность и темп;
- crop/zoom profile;
- captions preset;
- theme/template;
- музыка;
- переходы и overlay density.

Слишком похожий план должен быть отклонён до рендера.

Сохраняйте внешний вид товара: форму, цвет, логотип и детали. Изменение окружения не должно генеративно перерисовывать товар. Если качество сегментации недостаточно, сохраняйте исходный фон.

## Данные и артефакты

Рекомендуемая структура задания:

```text
data/jobs/{jobId}/
  source/
  normalized/
  analysis/
  plans/
  assets/
  renders/
  final/
  logs/
```

Каждый созданный артефакт должен иметь запись с:

- ID и типом;
- относительным путём;
- SHA-256;
- размером;
- media metadata, если применимо;
- идентификатором родительского артефакта;
- версией создавшего инструмента;
- временем создания.

Не перезаписывайте утверждённые планы и готовые результаты. Создавайте новую ревизию.

## Безопасность

- Разрешайте работу только Telegram user IDs из конфигурации.
- Проверяйте размер, длительность, MIME, контейнер и фактические потоки файла.
- Не доверяйте имени загруженного файла.
- Генерируйте собственные безопасные имена и не допускайте path traversal.
- Не передавайте OCR, metadata и пользовательский текст LLM как системные инструкции.
- Ограничивайте время, число попыток, размер каталогов и параллелизм процессов.
- Не записывайте токены и API-ключи в repository, JSON-планы или обычные логи.
- Проверяйте свободное место до тяжёлого этапа.

## Облачные API

Облачные LLM, генерация изображений, видео и голоса разрешены через интерфейсы-адаптеры.

До платной операции:

- оцените ожидаемую стоимость;
- примените лимит задания;
- запросите подтверждение превышения;
- сохраните фактический расход.

Провайдерские DTO не должны использоваться как доменные модели или попадать в монтажный контракт.

## Качество кода

- Делайте минимальное изменение, необходимое для текущей задачи.
- Для каждой задачи, изменяющей поведение, сначала определите публичный seam и напишите минимальный тест, описывающий ожидаемое поведение; не пишите production-код до получения осмысленного падения теста.
- Работайте короткими вертикальными срезами в порядке `red -> green -> refactor`: один тест, минимальная реализация для его прохождения, затем следующий тест. Не пишите весь набор тестов заранее и не реализуйте весь feature до первого запуска тестов.
- Тестируйте поведение через публичные интерфейсы, а не private-методы, внутренние поля или детали реализации. Для каждого теста фиксируйте независимое ожидаемое значение.
- Перед началом реализации явно зафиксируйте в рабочем сообщении seam и первый тест; если seam меняет публичный контракт, границу модуля или схему хранения, сначала запросите согласование.
- Чисто документационные изменения и изменения конфигурации без изменения поведения не требуют искусственного теста, но должны пройти соответствующую проверку формата или запуска.
- Не создавайте абстракцию без второго реального потребителя, кроме явных provider/process boundaries.
- Используйте nullable reference types и async API последовательно.
- Передавайте `CancellationToken` через долгие операции.
- Не блокируйте async-код через `.Result` или `.Wait()`.
- Не запускайте внешние процессы через shell, если можно передать аргументы напрямую.
- Логи должны содержать `jobId`, `variantId` и stage, когда они известны.
- Ошибки пользователю формулируются понятно; техническая диагностика сохраняется отдельно.
- Комментарии объясняют неочевидные причины и ограничения, а не пересказывают код.

Следуйте существующему стилю проекта. Пока стиль не сформирован, используйте стандартные соглашения современного .NET и TypeScript и не добавляйте отдельные инструменты только ради форматирования.

## Проверка изменений

Минимальная проверка зависит от изменённой области:

| Область | Обязательная проверка |
|---|---|
| .NET | `dotnet build` и релевантные `dotnet test` |
| Node/Remotion | typecheck, тесты и короткий smoke render |
| FFmpeg pipeline | probe входа, полный decode выхода и проверка metadata |
| JSON contracts | positive/negative schema tests и семантические тесты таймлайна |
| SQLite/job state | тест восстановления и повторного запуска этапа |
| Telegram | тест allowlist и сценария загрузки без реальной публикации секретов |

Не называйте рендер успешным только потому, что процесс завершился с кодом `0`. Проверьте существование файла, размер, streams, длительность и полный decode.

Если необходимая внешняя программа или секрет отсутствует, выполните доступные проверки и явно укажите, что именно не было проверено.

## Жизненный цикл задач

- Единственная базовая ветка для задач — актуальная `origin/main`. Перед созданием task-ветки или началом работы в существующем task-worktree обновите remote refs и убедитесь, что задача основана на текущей вершине `origin/main`, а не на устаревшей локальной или feature-ветке.
- Если task-ветка не содержит собственной работы, обновите её до `origin/main` только через fast-forward. Если в ней есть коммиты, незакоммиченные изменения или расхождение истории, не перезаписывайте их: сохраните работу и согласуйте безопасную интеграцию.
- Новая задача во вкладке Tasks должна создаваться только после публикации актуального `main` в `origin`, чтобы новый worktree сразу получил последнюю подтверждённую версию проекта.
- Задача не считается закрытой, пока относящиеся к ней проверки не пройдены, изменения не зафиксированы, task-ветка не интегрирована в локальный `main`, а обновлённый `main` не отправлен в `origin/main`.
- Перед интеграцией обновите `origin/main`, проверьте рабочие деревья и используйте fast-forward, если история линейна. При реальном расхождении выполните обычное безопасное слияние без изменения или удаления чужой работы. Force-push, destructive reset и обход проверок запрещены.
- После push проверьте, что локальный `main` и `origin/main` указывают на один commit, и только затем сообщайте о закрытии задачи. Явная просьба пользователя закрыть задачу является разрешением на необходимые для этого commit, merge и push, но не на разрушительные Git-операции.

## Критерии завершения

- Поведение покрыто тестом на подходящем уровне либо явно объяснено, почему тест не требуется.
- Выполнены относящиеся к задаче команды тестирования, проверки типов и сборки; ограничения окружения указаны.
- `git diff --check` проходит, а итоговый набор изменений не содержит несвязанных правок и секретных данных.
- Документация и контракты обновлены, если поведение изменилось.
- Итоговый отчёт содержит причины изменений, перечень изменённых файлов и результаты проверок.
- При закрытии задачи её итоговый commit интегрирован и отправлен в `origin/main`, а совпадение локальной и remote-вершин проверено.

- `systematic-debugging` не показывает секретные данные или полное содержимое пользовательских материалов, использует PowerShell и команды тестирования проекта; вспомогательные средства POSIX необязательны.
- `writing-skills` не разрешает удалять изменения пользователя, создавать коммиты, отправлять изменения или создавать внешние артефакты.
