# ADR 0001: Модульный монолит с Clean Architecture

## Статус

Принято.

## Контекст

AI Video Factory объединяет Telegram-взаимодействие, управление состоянием задания, анализ медиа, планирование, рендер и доставку. Эти возможности должны работать в одном процессе для простоты MVP, но их зависимости не должны превращаться в общие проекты `Core` и `Infrastructure`, в которых смешиваются разные бизнес-области.

## Решение

Система строится как модульный монолит. Первый бизнес-модуль называется `VideoProduction` и владеет жизненным циклом производства видео.

Каждый бизнес-модуль разделяется на проекты:

- `Domain` содержит бизнес-модель и правила;
- `Application` содержит сценарии использования и seams для внешних возможностей;
- `Infrastructure` содержит адаптеры внешних систем и хранения.

Зависимости направлены внутрь: `Infrastructure -> Application -> Domain`. Исполняемый `VideoFactory.Bot` является Host, Telegram-адаптером и composition root. Он подключает модуль, но не содержит бизнес-правил.

Межмодульное взаимодействие должно проходить через явные контракты. Общие проекты и `SharedKernel` создаются только при наличии как минимум двух реальных потребителей.

## Последствия

- Компилятор контролирует направление зависимостей между слоями модуля.
- Инфраструктурные детали остаются локальными для модуля.
- Число проектов выше, чем в обычном слоистом монолите.
- При появлении нового модуля потребуется определить его внешний interface и межмодульные контракты.

## Отклонённые варианты

- Общий `VideoFactory.Core`: со временем смешивает доменные модели разных модулей.
- Общий `VideoFactory.Infrastructure`: связывает независимые адаптеры и затрудняет локальные изменения.
- Слоистый монолит с модулями только в папках: не обеспечивает compile-time изоляцию.
- Один assembly на модуль: требует соглашений или дополнительных архитектурных тестов для контроля Clean Architecture.
